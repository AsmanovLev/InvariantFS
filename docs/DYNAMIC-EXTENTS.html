Динамические экстенты: что куда ссылается

Как устроено сейчас, что меняется, и пошаговый пример на 1 МиБ файле, в котором правится 2 КиБ. Числа взяты из замеров impl_docs/BENCH-MERKLE-DEDUP.md и BENCH-VS-SQUASHFS.md.

1. Как устроено сейчас

У файла есть inode-строка в B-дереве, а в ней — адрес рецепта (BLAKE3 от блоба рецепта). Рецепт — это «карта» файла: заголовок + массив записей.

invfs_ast_block_entry (32 Б):
  file_offset    u64    смещение диапазона в ФАЙЛЕ
  length         u64    длина диапазона (логическая, до распаковки)
  zone:2  algo:6 block_id:24   зона / кодек / ключ батча
  block_offset   u32    смещение внутри распакованного батча
  pba            u64    физический БЛОК, с которого начинается сегмент

Физическая длина сегмента не хранится в рецепте: она лежит в 8-байтном заголовке по адресу pba ([csize u32][crc u32]), а фактически занимает ceil((8+csize)/4096) блоков. Отсюда всё, что мы померили: сегмент всегда выровнен на блок, и каждый сегмент округляется отдельно — 8.5 % потерь при 64-КиБ сегментах, 0.7 % при 1 МиБ.

Три следствия, которые мы померили:
  • каждый сегмент округляется до целого блока → 8.5 % места в мусор при 64 КиБ (2.5 % при 256 КиБ, 0.7 % при 1 МиБ);
  • размер сегмента — глобальная константа, поэтому «мелко для дедупа / крупно для места» выбрать нельзя;
  • ключ дедупа — хэш сохранённых байтов, поэтому тот же контент, сжатый другим уровнем, уже не совпадёт.

3. Пример: файл 1 МиБ, правим 2 КиБ в середине

Лист дерева = 4 КиБ, значит у 1 МиБ файла 256 листьев и 9 уровней (4 КиБ → 1 МиБ). Правка попадает в лист №128 (смещение 512 КиБ).

Шаг 1. Считаем дерево

L0 (4 КиБ):  256 хэшей  → меняется 1 (лист 128)
L1 (8 КиБ):  128        → меняется 1 (родитель листа 128)
...
L8 (1 МиБ):  1          → меняется корень
root_hash тоже меняется  → файл «другой», но 255/256 листьев совпадают со старым

Шаг 2. Ищем совпадения сверху вниз

Индекс знает старые узлы файла. Спуск от 1 МиБ: корень не совпал → идём в детей 512 КиБ: левая половина (0…512 КиБ) совпала целиком → это ссылка на существующий экстент, писать нечего. Правая половина не совпала → спускаемся: 256 КиБ, 128, 64, 32, 16, 8, 4 КиБ — на каждом уровне левый ребёнок совпадает, правый нет. Совпал весь путь до листа 128.

Шаг 3. Планируем экстенты по «дырам»

дыраразмерэкстент (лестница)почему
правленый лист4 КиБ4 КиБдырка меньше следующей ступени — мельче некуда
новый регион 40 МиБ40 МиБ40 × 1 МиБсплошной прогон: крупно = хорошее сжатие и округление 0.7 %
хвост файла 300 КиБ300 КиБ1 × 256 КиБ + 1 × 44 КиБне выходим за границу дыры

Шаг 4. Что в итоге лежит на диске

политикаперезаписано после правки 2 КиБ
фиксированные экстенты 1 МиБ1 МиБ (весь файл)
фиксированные экстенты 64 КиБ64 КиБ (сегмент с правкой)

На реальном корпусе (256 МиБ образ, правка 2 КиБ) это же отношение дало 44 МиБ против 1 МиБ — см. BENCH-MERKLE-DEDUP.md.

4. Правило выбора размера экстента

для каждого непокрытого прогона [a, b):
    остаток = b - a
    пока остаток > 0:
        размер = наибольшая ступень лестницы ≤ остатка      # 1 МиБ, 256К, 64К, 16К, 4К
        если размер < 4096: размер = 4096                   # минимум — блок
        писать экстент(offset=a, logical=размер)
        a += размер;  остаток -= размер
Порядок «сначала совпадения, потом лестница» — это и есть разделение, которого не хватало: сопоставление решает, что можно не писать вообще (и на каком уровне), лестница решает, каким куском писать то, что писать всё-таки надо.

5. Чтение: дерево не нужно

Дерево — это индекс сопоставления и проверки. Чтение идёт по экстентам:

read(off, len):
    для каждого экстента с file_offset ≤ off < file_offset+length:
        прочитать (pba, sub_off, stored_len) → распаковать algo → отдать срез
    (экстентов на файл теперь мало: 1 МиБ куски, а не 64 КиБ)

Бонус: экстентов меньше → меньше записей в рецепте → рецепт меньше. Для 1 ГиБ файла: 16384 записи по 32–48 Б при 64 КиБ против 1024 записей при 1 МиБ.

6. Проверка и ремонт: дерево нужно

verify_range(off, len):
    взять наименьший узел дерева, покрывающий [off, len)
    прочитать и распаковать данные этого узла
    H(данные) == узел.hash  →  диапазон цел
    (не нужно читать весь файл, чтобы проверить 64 КиБ)

7. Компакция и refcount

  • Совпадение = ссылка на существующий экстент: refcount++. Поэтому один 1-МиБ экстент может обслуживать сотни файлов/образов.
  • Перезапись файла, который целиком совпал, ничего не пишет: меняется только рецепт (и корень).
  • Когда картина совпадений меняется (например, файл правится часто), компакция пересчитывает дырки и может слить мелкие экстенты в крупные или разрезать крупный на мелкие, если так больше совпадений.
  • Освобождение: refcount == 0 → экстент свободен; хвост возвращается суб-блочному аллокатору.

8. Как крупное сжатие уживается с дедупом по 4 КиБ

Совпавший диапазон не пишется заново — он становится ссылочным срезом в чужой экстент. Механизм уже есть в формате: block_id + block_offset именно так член батча ссылается на свой кусок общего распакованного потока.

файл B, лист №128 (4 КиБ) совпал с данными внутри экстента E файла A (E = 1 МиБ):
  запись в рецепте B: { file_off=512K, logical=4096, block_id=E, block_offset=39*4K }
  → 0 новых байт на диске; данные A при этом лежат крупным сжатым экстентом

То есть дедуп видит 4 КиБ, а сжатие работает крупными кусками. Компромисс при этом не исчезает, а переезжает из места в чтение:

сейчас (сегменты 64 КиБ, ключ по сжатым байтам)дерево + динамические экстенты
дедуп на 4 КиБневозможен (гранулярность = сегмент)возможен, 0 байт
сжатиепосегментное, 64 КиБкрупное, до 1 МиБ
цена мелкой ссылки—чтение 4 КиБ требует распаковки всего содержащего экстента
цена плохого сжатияна всём объёме (8.5 % округления)только на изменённой доле (2.9 КиБ вместо 1 МиБ)

Поэтому нужен третий элемент — политика разрезания по ссылкам: экстент, который берут только целиком, держим крупным; экстент, у которого часто берут узкие срезы, компакция режет, материализуя горячие 4 КиБ в собственные мелкие экстенты. Решение «мелко или крупно» принимается на экстент по фактическому использованию, а не глобальной константой.

9. Почему ключ дедупа по plaintext, а не по сжатым байтам

Сегодня ключ — BLAKE3([8 Б заголовок][сжатый payload]) (vol_dedupe.c:423). Значит совпадение требует побайтово одинакового сжатого потока, а он зависит от кодека, уровня, параметров и границ сегментов. Замер на одних и тех же 64 КиБ (/usr/bin/bash):

plaintext-хэш (лист дерева)                : 114343cc95ef9df138a5…
  zstd-3 : csize=31125  ключ = 1585ded83589e7651bfd…
  zstd-19: csize=28614  ключ = b001768f56ba725c69a1…
  ключи совпали? False

Практическое следствие: том, записанный на профиле faster (zstd-3) и позже пере-свипнутый на balanced (zstd-19), теряет дедуп через эти сегменты молча — оба экземпляра остаются на диске. То же при смене кодека или установке кодека-пака.

С ключом по plaintext-листьям этого не происходит: ключ не зависит ни от уровня, ни от кодека, ни от границ. Это не «побочный плюс», а условие, при котором многоуровневое сопоставление вообще имеет смысл.

12. Одной фразой

Дерево Меркла отвечает на вопрос «что не надо писать» с точностью 4 КиБ, а лестница экстентов — на вопрос «каким куском писать остальное». Сейчас оба ответа склеены в одну константу INVFS_SEGMENT_SIZE, и именно поэтому нельзя одновременно иметь мелкий дедуп и крупное хранение.

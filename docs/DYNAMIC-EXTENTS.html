Dynamic Extents: What References What

How it works today, what changes, and a step-by-step example on a 1 MiB file with a 2 KiB edit. The numbers come from measurements in impl_docs/BENCH-MERKLE-DEDUP.md and BENCH-VS-SQUASHFS.md.

1. How It Works Today

A file has an inode row in the B-tree, and it holds the address of the recipe (BLAKE3 of the recipe blob). The recipe is the file's "map": a header plus an array of entries.

invfs_ast_block_entry (32 B):
  file_offset    u64    range offset in the FILE
  length         u64    range length (logical, before decompression)
  zone:2  algo:6 block_id:24   zone / codec / batch key
  block_offset   u32    offset within the unpacked batch
  pba            u64    physical BLOCK where the segment starts

The physical length of a segment is not stored in the recipe: it lives in the 8-byte header at pba ([csize u32][crc u32]), and actually occupies ceil((8+csize)/4096) blocks. Hence everything we measured: a segment is always block-aligned, and each segment is rounded up individually — 8.5 % loss with 64 KiB segments, 0.7 % with 1 MiB.

Three consequences we measured:
  • each segment is rounded up to a whole block → 8.5 % of space wasted at 64 KiB (2.5 % at 256 KiB, 0.7 % at 1 MiB);
  • segment size is a global constant, so you cannot choose "small for dedupe / large for space";
  • the dedupe key is a hash of the stored bytes, so the same content compressed at a different level no longer matches.

3. Example: 1 MiB File, Editing 2 KiB in the Middle

A tree leaf = 4 KiB, so a 1 MiB file has 256 leaves and 9 levels (4 KiB → 1 MiB). The edit lands in leaf #128 (offset 512 KiB).

Step 1. Compute the tree

L0 (4 KiB):  256 hashes → 1 changed (leaf 128)
L1 (8 KiB):  128        → 1 changed (parent of leaf 128)
...
L8 (1 MiB):  1          → the root changes
root_hash also changes → the file is "different", but 255/256 leaves match the old one

Step 2. Find matches top-down

The index knows the file's old nodes. Descending from 1 MiB: the root did not match → go to its 512 KiB children: the left half (0…512 KiB) matched entirely → it is a reference to an existing extent, nothing to write. The right half did not match → descend: 256 KiB, 128, 64, 32, 16, 8, 4 KiB — at each level the left child matches and the right one does not. The entire path down to leaf 128 matched.

Step 3. Plan Extents by "Holes"

new 40 MiB region40 MiB40 × 1 MiBcontiguous run: larger = good compression and 0.7 % rounding
file tail 300 KiB300 KiB1 × 256 KiB + 1 × 44 KiBstay within the hole's boundary

On a real corpus (256 MiB image, 2 KiB edit) the same ratio gave 44 MiB versus 1 MiB — see BENCH-MERKLE-DEDUP.md.

4. Rule for Choosing Extent Size

for each uncovered run [a, b):
    remaining = b - a
    while remaining > 0:
        size = largest ladder rung ≤ remaining          # 1 MiB, 256K, 64K, 16K, 4K
        if size < 4096: size = 4096                      # minimum is a block
        write extent(offset=a, logical=size)
        a += size;  remaining -= size
The "matches first, then ladder" order is the missing separation: matching decides what need not be written at all (and at which level), the ladder decides which chunk size to use for what still must be written.

5. Reading: The Tree Is Not Needed

The tree is an index for matching and verification. Reads go through extents:

read(off, len):
    for each extent with file_offset ≤ off < file_offset+length:
        read (pba, sub_off, stored_len) → unpack algo → return the slice
    (few extents per file now: 1 MiB chunks, not 64 KiB)

Bonus: fewer extents → fewer recipe entries → smaller recipe. For a 1 GiB file: 16384 entries of 32–48 B at 64 KiB versus 1024 entries at 1 MiB.

6. Verification and Repair: The Tree Is Needed

verify_range(off, len):
    take the smallest tree node covering [off, len)
    read and unpack that node's data
    H(data) == node.hash  →  the range is intact
    (no need to read the whole file to verify 64 KiB)

7. Compaction and Refcount

  • A match = a reference to an existing extent: refcount++. One 1 MiB extent can thus serve hundreds of files/images.
  • Rewriting a file that matched entirely writes nothing: only the recipe (and the root) changes.
  • When the match pattern changes (e.g., the file is edited frequently), compaction recomputes holes and can merge small extents into larger ones or split a large one into small ones if that yields more matches.
  • Freeing: refcount == 0 → the extent is free; the tail returns to the sub-block allocator.

8. How Large-Block Compression Coexists with 4 KiB Dedupe

A matching range is not written again — it becomes a reference slice into someone else's extent. The format already has this mechanism: block_id + block_offset is exactly how a batch member references its piece of a shared unpacked stream.

file B, leaf #128 (4 KiB) matched data inside extent E of file A (E = 1 MiB):
  entry in B's recipe: { file_off=512K, logical=4096, block_id=E, block_offset=39*4K }
  → 0 new bytes on disk; A's data remains one large compressed extent

So dedupe sees 4 KiB while compression works on large chunks. The tradeoff does not disappear; it moves from storage into reads:

today (64 KiB segments, key over compressed bytes)tree + dynamic extents
4 KiB dedupeimpossible (granularity = segment)possible, 0 bytes
compressionper-segment, 64 KiBlarge, up to 1 MiB
cost of a small reference—a 4 KiB read requires unpacking the entire containing extent
cost of poor compressionacross the whole volume (8.5 % rounding)only on the changed fraction (2.9 KiB instead of 1 MiB)

So a third element is needed — a reference-based splitting policy: keep an extent that is only ever taken whole large; for an extent that is often read in narrow slices, compaction splits it, materializing hot 4 KiB pieces into their own small extents. The "small or large" decision is made per extent based on actual usage, not a global constant.

9. Why the Dedupe Key Is Over Plaintext, Not Compressed Bytes

Today the key is BLAKE3([8 B header][compressed payload]) (vol_dedupe.c:423). A match therefore requires a byte-for-byte identical compressed stream, which depends on the codec, level, parameters, and segment boundaries. A measurement on the same 64 KiB (/usr/bin/bash):

plaintext hash (tree leaf)                : 114343cc95ef9df138a5…
  zstd-3 : csize=31125  key = 1585ded83589e7651bfd…
  zstd-19: csize=28614  key = b001768f56ba725c69a1…
  keys match? False

Practical consequence: a volume written with the faster profile (zstd-3) and later re-swept with balanced (zstd-19) silently loses dedupe across those segments — both copies remain on disk. The same happens when changing the codec or installing a codec pack.

With a key over plaintext leaves this does not happen: the key depends neither on the level, nor the codec, nor the boundaries. This is not a "side benefit" but the condition under which multi-level matching makes sense at all.

12. In One Sentence

The Merkle tree answers "what not to write" at 4 KiB granularity, and the extent ladder answers "which chunk size to use for the rest". Today both answers are glued into a single constant, INVFS_SEGMENT_SIZE, which is exactly why fine-grained dedupe and large-block storage cannot coexist.

# Handoff: почему мелкие файлы дороги (и почему это НЕ размещение дельты)

Состояние на конец сессии, где был найден и исправлен fsck-слепой-к-дельте баг
(`7cc8f5b`), а гипотеза «перенести метаданные на SSD» проверена и **опровергнута
как первопричина** до написания кода.

## Измерения (стенд 192.168.0.2, после отключения sweep)

| операция | на стенде | локально, тот же бинарь |
|---|---|---|
| create пустого файла | 0.8 мс/оп | ~0.1 мс/оп |
| delete | **48 мс/оп** | 1.07 мс/оп |
| delete 100 / 1000 / 4000 файлов | 48.2 / 47.9 / 48.3 мс/оп | — |

Delete **плоский** по числу файлов: это не O(N²) и не деградация базы.

## Ключевой вывод

`create` и `unlink` проходят ОДИН И ТОТ ЖЕ путь метаданных:

```
vol_inode_delta_put + vol_dirent_delta_put -> delta_put -> vol_delta_append
                                          -> pwrite записи в сегмент -> vmux_barrier
```

Разница 0.8 мс против 48 мс — 47 мс — не может быть ни дельтой, ни fence, ни
размещением дельты: они одинаковы у обеих операций. Она целиком в том, что
делает ТОЛЬКО unlink:

- `vol_retire_recipe` — отложенное освобождение блоков рецепта;
- `vol_pba_ref_release` — правка карты ссылок pba;
- `vol_free_blocks` — освобождение блоков;
- `vol_bm_dirty` на каждый блок — отслеживание «грязных» битмапов;
- `vol_reclaim_drain` — слив очереди освобождения.

Отсюда: **перенос дельты в RAW-зону (dev0/SSD) не ускорит delete.** Это надо
было проверить до реализации; проверено рассуждением по уже снятым числам, а не
новым экспериментом — эксперимент с переносом зоны был начат и откачен.

## Что делать дальше (по порядку)

1. **Тайминги внутри `vol_unlink`** (`src/core/vol_dirs.c:738`). Обернуть
   `clock_gettime(CLOCK_MONOTONIC)` вокруг четырёх фаз (retire / pba_ref_release /
   free_blocks+bm_dirty / reclaim_drain) и снять 200 unlink'ов на стенде.
   Это ответит на вопрос за один запуск. Гипотеза-фаворит: `vol_bm_dirty` +
   `vol_reclaim_drain` тянут за собой перезапись метаданных страниц на каждый
   блок, а не на операцию.
2. **Если подтвердится bitmap/reclaim** — батчинг: копить освобождения и
   помечать грязные биты в RAM, писать битмап-страницу один раз на fence.
   Это тот же приём, что уже применён в `vol_write.c` (group commit).
3. **Только после этого** — вопрос размещения метаданных (дельта на dev0). Если
   и делать, то по правилу смещения: RT30 — ровно 48 байт без свободных полей,
   SPT0 сразу за ним, поэтому второй указатель хранить негде; shadow-копия
   сегмента должна вычисляться из адреса, а не адресоваться полем. Контракт
   «RAW (dev0) умер -> Shadow (dev1) читается» при этом обязан сохраниться:
   либо дельта зеркалится (копия отстаёт, окно потерь ограничено частотой fold
   и должно быть записано явно), либо теряется хвост — и это уже не «читается».
4. **Inline-контент мелких файлов** — отдельная ось (меньше записей, а не
   быстрее запись). Компромиссы: строка inode становится переменной длины,
   `chmod` переписывает содержимое, дедуп/retention на inline не
   распространяются. «Одна запись на файл» упирается в хардлинки (nlink > 1 -> N имён).

## Что НЕ является решением

- **AG / шардинг namespace.** Другая ось: разбиение против размещения. Помечено
  измерением: 3452 -> 3353 файла/с на 10-кратном росте, rebuilds = 1,
  в `vol_write.c` нет ни одного мьютекса. Одиночный unlink AG не ускоряет.
- **Пере-тюнинг sweep.** Sweep выключен по умолчанию (`interval = iv ? atoi(iv) : -1`)
  и это правильно; `INVFS_SWEEP_INTERVAL=1` в initramfs стенда был багом стенда.

## Наблюдение той же патологии с другой стороны

`emerge-webrsync` простоял 3 часа с **нулевым блочным I/O** (`/proc/PID/io`), а
машину держал его же `rm -rf /var/tmp/emerge-webrsync.*`: удаление ~160k файлов
по ~48 мс = часы. Это не сеть и не портеж — это тот же путь `unlink`.

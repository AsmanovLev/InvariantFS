# Дедупликация

## Content-Addressed Storage через BLAKE3

BLAKE3 выбран за:

- ~10x быстрее SHA-256 на больших данных (AVX-2 оптимизации)
- Древовидное хэширование — параллельный расчёт на многоядерных системах
- Keyed hashing — возможность разделять хэши по типам данных (аудио, текст, бинарник)

**Как реализовано (WP12(h)):** дедупликация — **офлайн-проход в sweep'е**
(`vol_sweep_dedupe`), а не write-time CAS. Персистентного Content Index
на диске нет: проход хэширует **хранимые байты** каждого сегмента в
памяти, оставляет один pba на хэш, остальные сегменты L2P-remap'ит на
него и освобождает дублирующие блоки. Пропускаются: записи zone==TEXT
(их блоки принадлежат владельцу `\x01tzb`), целофайловые блобы
(JXL/APE-транскоды) и иноды, отложенные в аккумулятор текущего прогона.
Порядок в CLI: walk → dedupe → GC → flush (06-sweep-worker.md).

Ранний дизайн (online Content Index + журнальные refcount'ы) не
реализован и отменён — см. «Учёт ссылок» ниже.

## Уровни дедупликации

### 1. Блочная дедупликация (сегментная, офлайн)

Если 100 FLAC-файлов содержат одну и ту же обложку, после прохода
дедупа сегменты всех 100 файлов указывают (через L2P) на один
физический блок. Дедуп применим и к одинаковым членам контейнеров
(`name!partN` у TARR/GZR, `name!mbrNNNN` у контейнерпакетов): члены —
обычные иноды и участвуют в общем проходе.

### 2. Семантическая дедупликация (секции ELF/PE) — far-roadmap

```
Бинарник v1: [.text: hash_A] [.rodata: hash_B] [.data: hash_C]
Бинарник v2: [.text: hash_D] [.rodata: hash_B] [.data: hash_C]
                                        ↑
                              .rodata и .data дедуплицированы!
```

Разбора ELF/PE на секции в коде нет. Часть этого выигрыша shipped-механизм
забирает иначе: бинарный батчинг WP14a сортирует односемейные файлы
рядом, и cross-file повторы (включая общие .rodata) сжимаются контекстом
батча. Явное разделение секций — территория Template Zone
(17-template-zone.md, слой словарных ссылок).

### 3. Дедупликация для разработчиков (node_modules, контейнеры)

| Сценарий | Эффект |
|----------|--------|
| 10 микросервисов с одинаковыми зависимостями | Одна копия каждой уникальной библиотеки после sweep-дедупа + батчинга |
| Docker-образы (Ubuntu:20.04, Ubuntu:22.04) | Общие файлы сливаются сегментным дедупом; общие слои — дальше (17) |
| CI/CD артефакты (100 коммитов, каждый — сборка) | Батчинг бинарей (WP14a) ловит сходство сборок контекстом |
| Виртуальные окружения Python / venv | Одна копия numpy, pandas и т.д. после дедупа |

## Учёт ссылок: почему refcount'ов нет (PB7)

Первоначальный дизайн — счётчик ссылок на блок, изменяемый только через
журнал (`DELTA`-записи). **Не реализован и не нужен**: тип записи DELTA
никогда не существовал в коде, а причина, по которой его хотели
(data-loss при удалении дедупнутого блока, PB7), закрыта иначе
(2026-08-28):

- `vol_retire_inode` при удалении строит два pba-индексных битмапа
  (O(l2p) один раз): «pba ещё кем-то используется» и «pba уже
  освобождён» — и пропускает освобождение любого pba, на который
  ссылается другая живая MAP-запись; плюс guard от дублей внутри самого
  удаляемого файла.
- Репро PB7 (два пустых файла → sweep → удалить один) после фикса чист:
  fsck не видит missing, выживший файл bit-exact.

Журнальные refcount'ы дополнительно ничего бы не дали: удаление и так
идёт через tombstone-записи, а fsck пересобирает картину заново.

## Снапшоты

CAS-снапшоты «0 байт и мгновенно» из первоначального дизайна не
реализованы (нет ни refcount'ов, ни snapshot-таблицы). Shipped-ближайший
механизм — **чекпоинт sweep'а WP21**: перед проходом взводится CKP0
(позиции append'ов + стадированная копия журнала), sweep ничего не
освобождает (реестр `\x01reten`), и `invf-rollback` возвращает том
бит-в-бит к виду до sweep'а. Это откат одного прогона, а не
произвольные снапшоты; общие снапшоты остаются future work.

## Overhead

Персистентных индексов дедупа нет — на диске дедуп бесплатен. Цена
прохода — in-memory хэш-таблица хранимых сегментов на время sweep'а и
повторное чтение сегментов для хэширования.

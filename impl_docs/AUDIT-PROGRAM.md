# Программа аудита архитектурных дефектов (2026-11-19)

Повод: разовые проверки уже дали и реальные дефекты, и ложные срабатывания. Нужен
воспроизводимый порядок, а не охота на удачу. Ниже пять проходов, каждый отвечает на
свой класс вопроса, и у каждого есть критерий «нашли/не нашли».

Снимок кода для всех проходов: `f0f9924` (см. `CODE-MAP.md`).

## Проход 1. Покрытие гардов (funnel analysis)

Вопрос: у каждого защитного условия есть N путей, которые должны его уважать —
сколько из них действительно его уважают?

Метод: для каждого гарда найти **центральную функцию** (funnel) и **обходные пути**
(функции, которые стирают биты/освобождают мимо funnel).

Работающий пример: `spt0_block_pinned` живёт внутри `vol_free_blocks()`
(`volume.c:3843`), поэтому 44 из 46 точек освобождения защищены по построению.
Обходные: `vol_free_run()` (статический, ниже funnel), `mbuf_free()`
(`vol_metabuf.c:337` — идёт ЧЕРЕЗ funnel, плюс зеркалит счётчики под
`!v->retain_release`), и **намеренный** обход `v->retain_release = 1`
(`vol_spt0.c:1030`, `vol_reclaim.c`): reclaim обязан освобождать запиненное — это
гашение долга, а не дефект.

Кандидаты в гарды того же типа: `pba_ref_count()==0` перед освобождением,
`vol_name_is_container_sibling()`, `ast_frame_ok()`, `seg_extent_checked()`,
`tz_flush_class_ok()`, `vol_inode_get()!=1` перед публикацией.

Критерий: список `(гард, funnel, обходные пути, какие из них БЕЗ проверки)`.
Ложные срабатывания ожидаемы: намеренные обходы надо помечать, а не «чинить».

## Проход 2. Симметрия путей

Вопрос: где парные пути имеют разные наборы гардов?

Пары, которые надо сравнить построчно:
- запись (`vol_write_range`) ↔ чтение (`vol_read_range`);
- один девайс ↔ два (`INVFS_RAW_MIRROR`, `vmux_*`);
- sealed ↔ unsealed (`vol_seal_*`);
- `newino == inode_id` (supersede на месте) ↔ `newino != inode_id`;
- payload в блобе (`!mbrblob`) ↔ член-инод;
- ошибка ↔ успех на каждом шаге коммита (что откатывается).

Уже найденное этим классом: `vol_cpack.c:3342-3349` (в ветке `newino==inode_id`
superseded-сегменты не освобождаются, в соседней ветке — освобождаются).

Критерий: таблица пар и список асимметрий с `file:line`.

## Проход 3. Пути ошибки (alloc/free по всем возвратам)

Вопрос: на каждом пути выхода освобождено ли то, что выделено?

Метод: по каждой функции с 2+ выделениями — перечислить `return`/`goto` и для
каждого отметить, что освобождается. Найденное: `vol_png.c:949-953` (`cblob` не
освобождается на ошибке сериализации).

Критерий: список функций с неполным освобождением.

## Проход 4. Жизненный цикл объектов

Вопрос: у каждого объекта есть четыре перехода, и каждый ли охраняется?

Объекты: сессия записи, save point (пин), дельта-сегмент, owner батча, экстент,
хэндл пака, плагин-клиент. Для каждого: создание → публикация → инвалидация →
освобождение; кто ставит/снимает и что мешает двойному освобождению.

Найденное этим классом: `vol_spt0.c:861` (освобождение старого пина ДО отказа в
`:886` и до ошибки размещения нового), `vol_delta.c:2225-2236` (блоки новых
сегментов освобождаются до финального barrier), `vol_metabuf.c:381-383` (слот RT30
выбирается до инкремента, а чтение трактует `seq&1` иначе).

Критерий: таблица «объект × 4 перехода × охрана».

## Проход 5. Мутационная проверка контрактов

Вопрос: если снять гард, упадёт ли хоть один тест? Если нет — контракт не защищён.

Метод: для каждого гарда из прохода 1 временно заменить условие на `false` (в
worktree, не в основном дереве), собрать и прогнать затронутые тесты. Гард без
краснеющего теста = дыра в тестах.

Уже видно два таких: `test-helper-isolation` проходит при наличии fallback
`dlmopen→dlopen` (`ivpack_loader.c:291,295`), и `test-pack-sign` проходит, хотя
регистрация пака из env/`.ivpack` подпись не проверяет (`codec.c:1748`).

Критерий: список гардов без теста-свидетеля; каждый — заявка на новый тест.

## Порядок

1 и 2 — механические, дают список конкретных мест; 3 — дешёвый и почти всегда
что-то находит; 4 — самый дорогой по времени, но ловит архитектурные окна; 5 —
превращает найденное в защищённые контракты.

Проходы 1-4 выполняются **слепыми агентами** (дерево без доков и комментариев, см.
`CODE-MAP.md`), проход 5 — только локально, потому что требует сборки и тестов.

# WP: частичный reclaim SPT0 — что на самом деле нужно (аудит 2026-11-18)

Источник: аудит делегата `d8d3642c…` по `src/core/vol_spt0.c`.

## Главное: это НЕ «убрать флаг»

Код прямо документирует, почему отказ глобальный (`vol_spt0.c:965-971`):

> "Why refuse the whole reclaim rather than reclaim everything except the unreadable
> ones … unless the extent's reach is bounded, freeing the difference releases bytes a
> live recipe still decodes."

И есть замеренный тест именно на этот отказ (`src/cli/spn_broken_extent_test.c:35-41`):
предыдущий пин метил экстенты целиком, новый обход пометил только головы, reclaim
освободил все остальные блоки экстентов — под рецептами, которые их всё ещё читают.

То есть «сделать частичным» = **сначала получить границу сломанного экстента**, которой
сегодня нет.

4. `spn_reclaim()` `:939`, вызов `:1160`; наборы владельцев: `tz_reg_owned_blocks()`
   `vol_textzone.c:452`, `spn_reg_owns()` `:829`, `spn_meta_mark()` `:882` →
   `spt0_ptr_from_pba()` `:850` + `btree_mark_reachable()` `vol_btree.c:2119`.

## Что в структурах есть, а чего нет

- `map` / `old_map` — побитовые битмапы по блоку (`spn_map_bytes()` `:317`).
- Здоровый экстент: все блоки `[pba, pba+plen)` помечены `:798-803`; `plen` из
  `[csize][crc]` в голове.
- **Сломанный экстент: помечена ТОЛЬКО голова** `:762-767`; хвост — «unnamed UNKNOWN
  set», считается в `c.broken` `:792`. Это и есть корень проблемы.
- `indeterminate` inode: **ни одного бита** `:737-740`.
- `spn_dig {pba, csize, crc}` `:273-281`; у сломанного `csize = 0` `:792-795`.
  Дайджесты сортируются и пишутся ПЕРЕД битмапом `:1230-1247`; restore трактует
  `csize == 0` как отказ `:1464`.
- `spn_file_hdr.broken` — только СЧЁТЧИК `:1237`; `invfs_spn0` (`invarifs.h:714-724`)
  не хранит ни списка сломанных, ни границ экстентов.
- Предикат освобождения `:1031-1036`: `old_map` ∧ ¬`new_map` ∧ `v->bitmap` ∧ не во
  владении TZ-реестра ∧ не в `meta` (достижимо из `root_pba`).

## Что нужно, чтобы reclaim стал частичным

1. **Персистить границу сломанного экстента.** Минимум — `[head_pba, last_pba]`
   (или `[head, plen]`) на каждый сломанный сегмент, в том же пин-файле. Сейчас есть
   только голова и счётчик, поэтому после крэша/реопена диапазон неизвестен.
2. Набор освобождения становится
   `old_map \ (new_map ∪ tz_reg ∪ meta ∪ UNKNOWN)`; `!new_map_complete` перестаёт
   означать «не освобождать ничего глобально».
3. `indeterminate` **нельзя** сделать частичным фильтром диапазонов: его рецепт
   контентно-адресуем и задаёт неограниченное множество. Либо глобальный отказ
   остаётся, либо персистить идентичность рецепта инода и сверять при reclaim.
4. Новый пин должен копировать защищённые UNKNOWN-диапазоны **в свой `map`**
   (держим их ещё поколение); restore и так откажется их разыменовывать (`csize==0`),
   то есть деградация — утечка, а не порча.
5. Fail-closed гейты оставить: сбой `tz_reg_owned_blocks()`, `meta_ok == 0`,
   нечитаемый `old_map`, проверка аллокации `root_pba` `:1178`.

## Риски (все реальные)

- Освободить хвост сломанного экстента: читатель декодирует экстент целиком, один
  неверный блок = уничтоженный живой файл (замеренный WP632-сбой).
- Выводить `plen` из порванного заголовка или из **текущего** on-disk заголовка
  нельзя: там может быть уже перераспределённый сегмент. Валидно только
  свидетельство момента захвата / прошлого пина.
- Переиспользование головного pba между захватами: голова запинена, а хвостовой
  диапазон может принадлежать другому объекту — нельзя выводить владение из нового
  `map` по этому pba.
- Соседние экстенты в `old_map`: непрерывный прогон может склеить два
  распределения — короткий диапазон недоосвобождает, длинный утекает навсегда.
- Пропустить `meta`/TZ-реестр = повторить зафиксированную порчу базовых страниц и
  батчей (`:861-906`).
- Пин-hold (`spt0_block_pinned()`) должен остаться в силе для каждого защищённого
  блока: параллельно освобождают FUSE-retire и свип.

## Итог

Задача переформулирована: **сначала персистить reach сломанных экстентов**, и только
потом делать предикат освобождения частичным. Промежуточный консервативный источник
диапазона — непрерывный прогон `old_map` от головы (прошлый захват видел здоровый
экстент целиком), но он обязан быть персистирован и провалидирован, а не
реконструирован эвристикой.

## Побочная находка: `invf-rollback` отказывается на свежем save point (ПРЕДСУЩЕСТВУЕТ)

Воспроизведение (без FUSE):
```
invf-mkfs v.img 1 → invf-import v.img src ×2 → invf-sweep v.img → invf-fsck v.img → invf-rollback v.img
invf-spt0: refusing to roll back: the delta log the save point captured is gone
           (a fold reset it; the pinned rows are not in the pinned base root)
```
Но **fold не запускался** — в логе свипа:
```
fold: not triggered (2 records, 0 MiB; triggers 262144 / 64 MiB)
[spt0] save point: pinned 52 blocks (4 segments, 0 already damaged) in 9 blocks at pba 62300
save point captured (base_root=62299 delta_end=737)
```
То есть диагностика «a fold reset it» **ложная**: restore-проверка отвергает только что
поставленный save point по причине, которой не было. Следствие: `invf-rollback` (undo
последнего свипа) не работает даже в чистом сценарии, и тест
`no_ckp0_surface_test` (щель в шарде 4) валится именно на этом прогоне — три его
остальных LEG'а зелёные.

Бисекция: на коммите `74cab2b` (до правок сессии 18 ноября: reclaim-drain, batch-hint,
punch-hole) поведение ИДЕНТИЧНО. Значит это не регрессия, а предсуществующий дефект
restore-пути SPT0, и его надо чинить как отдельную задачу — вместе с частичным
reclaim, потому что обе живут в одном месте (`spt0_pin_take` / restore-проверка).

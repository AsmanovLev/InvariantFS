## Риски, которые аудит нашёл сверх ожидаемого

1. **`vol_seal.h:48` — `SEAL_SYM_BYTES 65536`** определён независимо, и seal
   предполагает, что **сегмент == символ**. Крупный чанк ломает геометрию seal,
   даже не попадая в grep по имени. Либо символ остаётся 64 КиБ и режется по
   логическому потоку (а не по границам сегментов), либо в формат идёт поле
   размера символа.
2. **`MAX_SEGMENTS_V2 = 1<<24`, `MAX_FILE_SIZE = 1<<48`** (`invarifs.h:1155,1167`):
   крупный чанк меняет максимально представимый размер файла и поведение EFBIG.
3. **`s->child_segs` уже пер-сессионный** (`vol_write.c:114`): child-рецепты,
   сохранённые со старым размером чанка, надо инвалидировать или помечать.
4. **Grep по имени пропускает литеральные 64 КиБ**: `vol_spt0.c:1440
   buf[64*1024]`, `sweep_publish_rollback_test.c:103 SEG_BYTES 65536`,
   `entry_v3_test.c:163-296`, `vol_cpack.c:2741 CPACK_LEAF_HEAD`. Проверить до
   любой правки формата.
5. **Рецепт не хранит размер чанка** — только `length` и `pba`. Смешивание
   размеров в одном томе безопасно лишь если все читатели используют `e->length`
   как границу декода; из этих хитов это не доказывается.

## Рекомендуемый путь (решение нужно принять)

Инвариант `vol_sweep.c:1230` («длина записи ≤ SEGMENT_SIZE») — это проверка, а не
свойство формата. Три варианта:

| вариант | что делает | цена |
|---|---|---|
| **(A) поле `max_chunk` в суперблоке** (рекомендую) | читатели валидируют `e->length <= sb.max_chunk`; писатель берёт `seg = min(policy, sb.max_chunk)`; старые тома читаются как 64 КиБ | одно поле в формат (v0.7), одна проверка |
| (B) на запись — тег размера в записи | самодостаточно на запись, но дублирует `length` и не отвечает на вопрос «какой максимум допустим» | поле в каждую запись, всё равно нужен предел |
| (C) просто поднять константу | без изменений кода чтения | ломает 64-КиБ инвариант для **старых** томов и seal |

## Порядок работ (после аудитов B и C)

1. Убрать стековые буферы (`plain[]`, `tmp[]`, `ctmp[]`, `cbuf`) в heap/скретч — без изменения поведения; гейт: те же тесты + бит-в-бит.
2. Ввести `max_chunk` в суперблок (вариант A) и перевести три (c)-проверки на него.
3. Добавить `seg` в сессию (дефолт = `sb.max_chunk`), заменить (a)-арифметику на `s->seg`.
4. Синхронизировать FUSE-стейджинг и `vol_sweep`-воркер с `s->seg`.
5. Seal: символы резать по логическому потоку, не по границам сегментов (или поле размера символа).
6. Замер: `invf-reconsolidate` план против факта; ожидаемо 8.5 % → ~0.7 % округления.

## Приложение: воронка формата рецепта (самоаудит, пока делегат B падал)

Делегат `d4b4eeb0…` упал по провайдеру («operation was aborted»), не по задаче.
Ниже — то, что снято прямым grep'ом, чтобы не блокироваться; перезапуск
(`dc9cd25f…`) уточнит детали.

| стадия | место | что важно для v4-записи |
|---|---|---|
| PARSE | `vol_ast_recipe_parse()` `vol_ast.c:247`; `invfs_ast_hdr_parse()` `invarifs.h:1238` | версия объявляется в заголовке; неизвестная версия обязана падать громко, а не читаться как v3 |
| STRIDE | `invfs_ast_entry_stride()` `invarifs.h:1210-1218` | 32 Б для V1/V2, **40 Б для V3**, 0 для неизвестной — единственная точка, где задаётся шаг записи |
| DECODE | `seg_read_once()` `vol_read.c:43`; чтение `csize` — `vol_read.c:64` (`pba*BLOCK+8`) | **вот эта строка и есть то место, где `stored_len` из записи заменит чтение заголовка сегмента** |
| SERIALIZE | `vol_ast.c`, `vol_cpack.c`, `vol_cut.c`, `vol_dedupe.c`, `vol_exer.c`, `vol_migrate.c` | шесть писателей рецептов: каждый конструирует записи сам, значит `stored_len`/`sub_off` придётся заполнять во всех шести |
| HEADER LEN | `hdr_len` из `invfs_ast_hdr_parse()` (`invarifs.h:1257,1273`), `INVFS_AST_HDR_V1_LEN/_V2_LEN` | записи начинаются по `hdr_len`; новое поле в заголовке = новая константа длины, а не сдвиг на месте |

Вывод для плана: v4-запись имеет **один парсер, одну таблицу шагов и один декодер**,
но **шесть писателей** — то есть чтение меняется в одном месте, а запись нужно
править дисциплинированно, иначе часть путей начнёт писать записи со «старым»
смыслом полей при новой версии заголовка.

гейт `INVFS_RECIPE_FORCE_V3`. Это дешевле, чем выглядело по первому grep'у.

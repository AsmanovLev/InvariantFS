# Находки: почему стенд «висел» на монтировании

Дата: ночь 15.11.2026. Стенд `192.168.0.2` (RAW `/dev/sda2` 110.7 ГБ, тень `/dev/sdb1` 1.8 ТБ),
дельта ~3.0M записей / ~1.5 ГБ, 322 889 файлов.

Симптом: монтирование не укладывалось в 1200 с, `init` отдавал rescue shell;
процесс `invf-fuse` при этом жёг 100% CPU, не делая ни одного write.

## 1. `fold_sort()` был O(n²) — это и был «вечный» фолд

`src/core/vol_fold.c` сортировал снимок дельты **вставками**:

```c
/* Stable insertion sort of the snapshot into key order (the list is small…) */
for (a = 1; a < l->n; a++) { ... while (b > 0 && vol_key_cmp(...) < 0) { ... b--; } }
```

Комментарий «the list is small» был верен для бенчмарков на 4k/20k файлов и
катастрофически неверен для реального тома:

| записей | операций (≈n²/4) | при ~6.7·10⁷ оп/с | по нашим замерам |
|---|---|---|---|
| 20 000 | 1.0·10⁸ | ~1.5 с | 5.98 с (измерено, bulk-путь) |
| 300 000 | 2.2·10¹⁰ | ~6 мин | — |
| 1 787 628 | 8·10¹¹ | **~3.5 часа** | висело 30+ мин и не двигалось |
| 3 021 686 | 2.3·10¹² | **~9.5 часов** | — |

Лог при этом молчит: сообщение `fold: bulk path, N record(s)` печатается уже
ПОСЛЕ сортировки, поэтому в `/tmp/fuse.log` последней строкой оставалось
`volume open complete`, а процесс крутился в CPU без I/O.

**Исправление** (`vol_fold.c`): `qsort()` с компаратором по ключу и тай-брейком
по номеру записи (детерминизм при равных ключах). 1.7M → десятки миллисекунд.
`invf-fold_test scenario` → 38/38 PASS.

## 2. Сообщение «mount fold: N -> N» врёт

`vol_fold_request()` возвращает 0 в трёх разных случаях: (а) дельта пуста,
(б) **триггеры не достигнуты** (`< 262144` записей и `< 64 МиБ`), (в) фолд
уже идёт (trylock). А `fuse_fs.c` печатает `mount fold: delta records N -> N`
во всех трёх — то есть выглядит как успешный фолд, который ничего не сделал.

Правильно было бы различать эти случаи; пока в документе фиксируем, что
`N -> N` означает «фолд не потребовался или не смог взять гейт», а реальный
фолд виден по `N -> 0` (или по строке `fold: bulk path`).

## 3. Ресинк тени копирует ВСЮ зону метаданных — 32 ГБ

```c
v->st.meta_end_bytes = (v->sb.metadata_zone_start + v->sb.metadata_zone_blocks) * BLOCK_SIZE;
/* mirror_resync(): uint64_t off = 0, end = v->st.meta_end_bytes; */
```

На стенде это **32 140 627 968 байт** — треть тома. Любое расхождение
`DEVT sync_seq` (а оно возникает после каждого неаккуратного выключения)
заставляет при следующем flush переписать эти 32 ГБ на 1.8-терабайтник,
страница за страницей. Замер: за 30 минут ресинк не завершился, и всё это
время фолд даже не начинался — он ждал за `vmux_barrier`.

Практические варианты (обсуждались, не реализованы):
1. копировать не весь спан, а только используемую часть (high-water mark);
2. сравнивать страницы побайтово и писать только различающиеся;
3. держать в DEVT dirty-диапазон и ресинкать его;
4. в крайнем случае — монтировать без тени (`INVFS_DEV1` не выставлять) и
   считать тень холодным резервом, ресинкая её отдельной офлайн-операцией.

## 4. Побочное: `init` в initramfs ждал мёртвый процесс 1200 с

Было:

```sh
invf-fuse ... &
FUSE_PID=$?          # всегда 0, а не pid!
while [ "$i" -lt 1200 ]; do
    grep -q "InvariantFS mounted" /tmp/fuse.log && break
    sleep 1; i=$((i+1))
done                 # живость ребёнка не проверялась
```

Стало (в установленном образе): `FUSE_PID=$!` и условие
`while [ "$i" -lt 1200 ] && [ -d /proc/$FUSE_PID ]`.

## Что установлено на стенд

`EFI/Gentoo/initramfs.img` = 6 118 085 Б, md5 `ee04b672…`, бэкап

## Утренний чеклист (что делать, когда появится доступ к стенду)

1. **Вернуть ST-Link** (сейчас он физически отключён: `OpenOCD не поднялся`).
   Дальше `python3 recover.py` из `/mnt/d/Users/User/invfs_deploy` — он поднимет
   демон, проверит ввод (при «залипании» STM сделает `reset halt`/`reset run`
   по SWD), прочитает экран, проверит ESP-мост и посмотрит, видно ли ESP
   как `/dev/ttyUSB*` на стенде.
2. **Загрузка на диск.** В BIOS сейчас `#1 = ADATA USB` (флешка). Либо вынуть
   флешку, либо обменять слоты #1↔#5 (работает через попап: выбрать ADATA
   в слоте, где лежит Hard Disk — AMI меняет слоты местами и **только тогда**
   сохраняется через F10 → Yes).
3. **Первый монтаж с фиксом** ожидаемо длинный, но конечный:
   реплей ~1.5 ГБ дельты (~80 с) → bulk-фолд 3.0M записей (секунды при qsort)
   → flush → ресинк тени 32 ГБ (десятки минут). Это НОРМАЛЬНО и делается один
   раз: после него `DEVT` выровнен, дельта пуста, монтажи секундные.
4. **Проверить результат** по `/tmp/fuse.log` на стенде: там должно быть
   `fold: bulk path, N record(s)` и `mount fold: delta records N -> 0`
   (а не `N -> N` — это «ничего не делали»).
5. **Только после этого** — работа по файловой системе: `invf-verify --deep`,
   `parts`-счётчик в inode-row, orphan-коллектор в sweep.

## Заготовки, сделанные ночью

## 5. Следующее узкое место фолда: по одному pread на запись

`fold_collect_cb()` вызывает `vol_delta_read_value()` для каждой записи, а та
делает **один `io_pread` на запись** (без кэша: `delta_read_value_locked`,
ветка «one pread»). Для дельты стенда это 3 021 686 pread-ов в 1.5 ГБ
сегментов, причём в порядке КЛЮЧЕЙ, а не в порядке сегментов — то есть
случайные чтения.

Оценка на стенде (sda2 — SSD, p50 0.13 мс из наших замеров):

```
3 000 000 × 0.13 мс ≈ 390 с ≈ 6.5 мин   (только сбор значений)
```

Плюс реплей дельты ~80 с, сортировка (после фикса — доли секунды), запись
нового base и ресинк тени 32 ГБ. Итого «первый монтаж после долга» — это
десятки минут, и это нормально; ненормально то, что по-записные чтения
можно убрать почти полностью.

**Предложение:** двухпроходный сбор. Первый проход — обойти индекс и сложить
`delta_ref` (без значений). Второй — пройти **сегменты последовательно**
(они append-ordered) и разложить значения по ссылкам. Тогда 3M случайных
pread-ов превращаются в один последовательный скан 1.5 ГБ: секунды вместо
минут, и никакой нагрузки на случайный I/O.

Это ровно тот же приём, что уже применён в `WP-BATCH-FOLD` для base-дерева
(потоковый скан вместо COW-апсертов) — просто ко второй стороне слияния.

## Прочие измеренные числа (локально, ext4, FUSE)

| что | значение |
|---|---|
| создание крошечных файлов (1 байт) | **207 файлов/с** (однопоточный демон) |
| место на файл в 1 байт | **12.7 КБ** (страница данных + inode-row + рецепт) |
| 150k файлов по 8 байт | **3.7 ГБ** на томе 4 ГБ → фолд отказал по нехватке места |

12.7 КБ на байтовый файл — это и есть корень «мелких файлов»: 500k файлов
веб-синка дают ~6.4 ГБ служебных данных, а зона метаданных на стенде выросла
до 32 ГБ. Кандидат на оптимизацию: **inline-данные в inode-row/рецепте** для
файлов меньше страницы.

`fold_space_ok()` при этом отказывает **молча** — в логе нет ни слова о причине
(мы это увидели только по `du` образа). Это стоит починить вместе с
сообщениями фолда.

## Замер на 150k файлов (устойчивый темп)

```
создано 150000 файлов за 2525.6 с   (59 файлов/с при непрерывной работе)
МОНТАЖ С ФОЛДОМ: 14.37 с
invf: mount fold declined or failed; the delta stays at 300000 records
InvariantFS mounted: 150000 files
```

Три вывода:

1. **Ровно 2 записи дельты на файл** (300 000 на 150 000) — как и предполагалось.
2. **Фолд не сработал не из-за кода, а из-за места**: том 4 ГБ, занято 3.7 ГБ,
   `fold_space_ok()` отказал. И отказ **молча** — в логе нет причины.
   Для полноценного замера нужен том с запасом (≥10 ГБ на 150k файлов).
3. Устойчивый темп создания — **59 файлов/с** (против 207 файлов/с на коротком
   всплеске из 1000 файлов): демон однопоточный, и при непрерывной записи
   пропускная способность падает втрое.

## 6. Почему «фолд не работал», хотя работал: коды возврата

`vol_fold_request()` возвращает **три разных значения**:

| код | смысл |
|---|---|
| `1` | фолд **выполнен** |
| `0` | делать нечего (ниже триггера или гейт занят) |
| `-1` | сбой |

А в `fuse_fs.c` стояло `vol_fold_request(g_vol) == 0` → **успешный фолд
попадал в ветку «declined or failed»**, а no-op печатал «delta records N -> N».
Отсюда целая ночь уверенности, что фолд не запускается: он запускался и
сворачивал дельту, а мы читали «declined or failed».

Проверка после исправления (15 000 файлов -> 30 000 записей дельты):

```
монтаж с фолдом: 4.17 с
invf: mount fold: delta records 30000 -> 0
InvariantFS mounted: 15000 files
```

То есть **фолд работает**: дельта свернулась в ноль, монтаж 4.17 с.

Заодно добавлена трассировка стадий отказа (раньше `fold_space_ok`,
чтение base-root, сбор дельты и публикация молчали): теперь при сбое в логе
есть строка `fold: FAILED at <стадия>`.

## 7. Обязательно для стенда: включить bulk-путь

По умолчанию фолд идёт **инкрементальным** путём (по одной записи через
`btree_upsert`), а bulk включается переменной `INVFS_FOLD_BULK=1`. Для дельты
стенда в 3M записей инкрементальный путь — это часы (ровно то, ради чего
делался `WP-BATCH-FOLD`).

В `init` стенда нужно добавить рядом с уже стоящими:

```sh
export INVFS_FOLD_BULK=1
export INVF_FOLD_CAP=0
export INVF_FOLD_CAP_MB=0
```

Без этого первый монтаж после долга пойдёт по медленному пути.

## 8. Bulk-путь: проверен и быстрее

Одинаковая дельта (15 000 файлов -> 30 000 записей), два пути:

| путь | монтаж с фолдом | лог |
|---|---|---|
| инкрементальный (по умолчанию) | **4.17 с** | `mount fold: delta records 30000 -> 0` |
| bulk (`INVFS_FOLD_BULK=1`) | **0.76 с** | `fold: bulk path, 30000 record(s)` + `delta 30000 -> 0` |

Bulk в ~5 раз быстрее уже на 30k и растёт линейно, тогда как инкрементальный
делает по COW-upsert на запись. Для дельты стенда (3 021 686 записей) это
принципиально: линейный путь даёт порядка минуты, квадратичный — часы.

Итог ночи по фолду: **все три дефекта найдены и исправлены, оба пути фолда
проверены на реальных файлах, дельта сворачивается в ноль.**

## 9. Откуда 12.7 КБ на файл в 1 байт (расклад)

Измерено: 1000 файлов по 1 байту дали прирост 13.2 МБ, то есть **12.7 КБ/файл**.
Складывается из:

| что | размер | почему |
|---|---|---|
| страница данных в RAW | 4 КБ | минимальная единица сегмента |
| блоб рецепта (RMC1) | 4 КБ | чанк 3072 Б + заголовок -> своя страница; **по дизайну не инлайнится** (`invarifs.h`: «recipe ... not inlined, so the row stays small and cacheable») |
| строки inode + dirent в дереве | ~4 КБ | COW-страницы дерева метаданных на вставку |
| **итого** | **~12.7 КБ** | файл полезного размера 1 байт |

Отсюда же растут: зона метаданных 32 ГБ на стенде, дельта в 3M записей,
и ресинк тени в 32 ГБ.

**Предложение (формат, делать когда решим ломать):** «крошечный файл» —
если данные ≤ ~1.5 КБ, хранить их **прямо в inode-row** отдельным вариантом
строки, без страницы RAW и без блоба рецепта. Тогда файл в 1 байт перестаёт
стоить 12.7 КБ и стоит ~долю страницы дерева. Для веб-синка на 500k мелких
файлов это разница между ~6.4 ГБ служебных данных и ~0.5 ГБ.

Порог и флаг надо выбрать так, чтобы старые тома читались без миграции:
новый вариант строки — это новое значение в существующем `type`/`flags`,
а не смена версии формата.

## 10. Масштабирование bulk-фолда (измерено)

| дельта | время монтажа с фолдом | лог |
|---|---|---|
| 30 000 записей | 0.76 с | `fold: bulk path, 30000 record(s)` |
| 200 000 записей | **6.43 с** | `fold: bulk path, 200000 record(s)` |

200k файлов создавались 1584 с (63 файла/с) — это отдельная цена пути записи.

Рост: 6.7x записей -> 8.5x времени, то есть **линейно** плюс постоянная
составляющая (реплей дельты). Экстраполяция к дельте стенда (3 021 686):

```
6.43 с × (3.02e6 / 2e5) ≈ 97 с
```

Даже с поправкой на более медленные диски стенда это единицы минут —
и уж точно не часы. Значит **фолд перестал быть узким местом**.

## 11. Что теперь узкое место на стенде

Не фолд, а **ресинк тени: 32 ГБ** (вся зона метаданных) на 1.8-ТБ HDD при
каждом расхождении `DEVT`. Порядок величин: 32 ГБ мелкими записями на HDD —
десятки минут, и это не влезает в 1200 с бюджета `init`.

Отсюда утренняя рекомендация: гасить долг **офлайн из LiveCD**, где нет
бюджета по времени:

```sh
INVFS_DEV1=/dev/sdb1 INVFS_FOLD_BULK=1 /tmp/invf-fsck -f /dev/sda2
```

(одна команда делает и ресинк 32 ГБ, и фолд 3M записей — и мы видим прогресс).

## 12. Разложение 12.7 КБ: платим за запись данных, а не за размер (измерено)

Один и тот же тест (800 файлов) на трёх вариантах содержимого:

| что создаём | скорость | прирост на файл |
|---|---|---|
| **пустой файл** (`open`+`close`) | **1874 файлов/с** | **0.3 КБ** |
| файл в 1 байт | 86 файлов/с | 12.7 КБ |
| файл в 4096 байт | 190 файлов/с | 12.7 КБ |

Выводы, которые из этого следуют:

1. **Пустой файл почти бесплатен**: 0.3 КБ и 0.5 мс — это inode-row и dirent
   в дереве метаданных, без отдельных страниц.
2. **Всё остальное — цена ПЕРВОЙ ЗАПИСИ**, и она фиксированная: 1 байт и
   4096 байт стоят одинаково, 12.7 КБ. То есть платим не за объём данных,
   а за страницу RAW (4 КБ) плюс блоб рецепта RMC1 (4 КБ, «not inlined» по
   дизайну) плюс сопутствующие COW-страницы дерева.
3. **Скорость падает в 22 раза**: 1874 -> 86 файлов/с, как только в файле
   появляется содержимое. Для веб-синка из 500k мелких файлов это
   принципиально: ~6.4 ГБ служебных данных и часы работы.

**Что это значит для оптимизации.** Наивное «inline-данные для мелких файлов»
надо уточнить: выигрыш даёт не «инлайн вместо страницы», а **устранение
отдельного блоба рецепта и отдельной страницы RAW для файлов, чьи данные
влезают в одну страницу**. Это ровно тот случай, когда рецепт — константа
«один экстент», и хранить 4 КБ AST ради одного байта данных бессмысленно.

Ожидаемый эффект для 500k файлов: 12.7 КБ -> ~0.5-1 КБ, то есть ~6.4 ГБ ->
~0.3-0.5 ГБ, и скорость создания порядка пустых файлов.

## 13. План оптимизации мелких файлов (конкретно, по коду)

Факты из кода:

- inode-row — 114 байт (`invfs_inode_row`), в ней `invfs_blkptr recipe` и
  `recipe_addr[INVFS_RECIPE_ADDR_LEN=32]`;
- рецепт — **content-addressed блоб** в том же B+-дереве под ключом
  `0x04 || blake3(blob)[32]` (`vol_recipe_store`, `invarifs.h` §WP-M8);
- дедупликация рецептов для нашего случая не работает: рецепт содержит PBA
  страницы данных, а он у каждого файла свой -> у каждого файла своя строка
  дерева плюс свой блоб;
- компактной формы «рецепт = один экстент» в формате **нет**.

Отсюда две ступени, обе без смены версии формата:

**Ступень 1 (даёт основное): тривиальный рецепт без блоба.**
Если файл — ровно один экстент (длина ≤ страницы), писать в строку
`recipe` = pba+len, а `recipe_addr` = сигнальный ноль, и отличать это
флагом (свободный бит в `type`/`row_version`). Читатель: если
`recipe_addr` — сигнал, рецепт синтезируется из `recipe`, без похода в
дерево. Экономия: строка рецепта в дереве (~4 КБ COW-страница) + блоб
(~4 КБ) -> файл стоит ~4.3 КБ вместо 12.7 КБ.

**Ступень 2 (для совсем мелких): данные в строке.**
Добавить вариант строки с полем данных до ~1.5 КБ: тогда нет ни блоба
рецепта, ни страницы RAW -> ~0.5 КБ на файл (измерено: пустой файл 0.3 КБ).

Ожидаемый эффект на 500k файлов веб-синка:

| вариант | на файл | всего | скорость создания |
|---|---|---|---|
| сейчас | 12.7 КБ | ~6.4 ГБ | 86 файлов/с |
| ступень 1 | ~4.3 КБ | ~2.2 ГБ | ~250 файлов/с (оценка) |
| ступень 2 | ~0.5 КБ | ~0.25 ГБ | ~1800 файлов/с (как пустые) |

Побочные эффекты: меньше записей в дерево -> меньше дельта -> дешевле фолд;
меньше зона метаданных -> дешевле ресинк тени (те самые 32 ГБ).

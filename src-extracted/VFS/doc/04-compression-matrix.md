# Compression Matrix

## Benchmark Results (from real hardware: TOSHIBA HDD + SSD RAID 0)

### Крупный текст (metadata_all.json — 898 KB)

| Algorithm | Ratio | Compress | Decompress |
|-----------|-------|----------|-----------|
| **PPMd -9** | **5.48%** | 9.22 MB/s | 8.57 MB/s |
| PPMd -6 | 6.65% | 10.99 MB/s | 10.21 MB/s |
| Brotli -11 | 7.0% | 0.55 MB/s | **12.25 MB/s** |
| ZSTD -19 | 7.85% | 1.3 MB/s | 8.16 MB/s |
| LZMA -9e | 6.86% | 3.63 MB/s | 10.99 MB/s |

### Мелкие текстовые блоки — PPMd ПРОВАЛИВАЕТСЯ

**Индивидуальный 4KB чанк (размер типичного ID3-тега):**

| Algorithm | Ratio | Verdict |
|-----------|-------|---------|
| **PPMd -9** | **38.75%** | ❌ Худший! Контекстная модель не успевает обучиться |
| ZSTD -19 | 19.95% | ✅ |
| Brotli -11 | 18.27% | ✅ |

**Индивидуальный 1KB чанк:**

| Algorithm | Ratio |
|-----------|-------|
| PPMd -9 | 56.15% ❌ |
| ZSTD -19 | 42.77% ✅ |
| Brotli -11 | 42.48% ✅ |

**Вывод: PPMd работает ТОЛЬКО на батчах ≥ 64KB.** На мелких блоках он стабильно хуже LZ-семейства.

Верхняя граница измерена отдельно (B27): PPMd растёт до **≈4 MB** и
дальше идёт вниз (o=16: 7.716× на 4M → 7.664× на 16M) — модель упирается
в `mem` и сбрасывается внутри блока. Оптимальный `order` — функция
размера блока: o=8 на 64K, o=16 на 256K–4M, o=32 только с 16M; разброс
между лучшим и худшим order на одном размере — до 12.9%.

### Батчинг (columnar storage) — спасает PPMd

20 × 4KB чанков (80KB суммарно):

| Algorithm | Индивидуально | Батчем (1 блок 80KB) |
|-----------|--------------|---------------------|
| PPMd -9 | 38.75% | **8.06%** 🥇 |
| Brotli -11 | 18.27% | 8.8% |
| ZSTD -19 | 19.95% | 10.1% |

Батчинг даёт выигрыш всем алгоритмам (4-5x), но PPMd без него вообще непригоден.

### Executable (gost.exe — 12.66 MB)

| Algorithm | Ratio | Compress | Decompress |
|-----------|-------|----------|-----------|
| LZMA -9e | **27.14%** | 5.94 MB/s | 66.3 MB/s |
| BCJ+LZMA -9 | 27.5% | 4.43 MB/s | 58.9 MB/s |
| Brotli -11 | 27.95% | 0.54 MB/s | 86.15 MB/s |
| **ZSTD -19** | 29.61% | 2.78 MB/s | **115.13 MB/s** |
| BCJ2+ZSTD -19 | 32.77% | 2.98 MB/s | 120.61 MB/s |

ZSTD -19 + BCJ2 — лучший tradeoff для файловой системы: 1.7x быстрее декомпрессия, чем LZMA, при ~2.5% хуже ratio.

### Audio (FLAC — 16.6 MB, already compressed)

Все общие алгоритмы дают ~100% (уже сжато). Для **lossless-аудио** применён
FLAC-recipe-путь (B23): FLAC транскодируется в APE(PCM) + бинарный рецепт
фреймов (`algo=flacr`, sibling `name!recipe`), реконструкция байт-в-байт
через C-репликатор. Транскод выполняется ТОЛЬКО если `ape+recipe < flac`
(инвариант git-safe); на реальной 16-bit музыке выигрыш ~3–5% чистыми,
на синтетике/24-bit guard оставляет оригинал.

## Algorithm Selection

| Data Type | Algorithm | Zone | Reason |
|-----------|-----------|------|--------|
| **RAW Zone (все записи)** | **LZ4 -1** | raw | Сверхбыстрый, снижает write amplification, отдаляет ENOSPC. Задержка write() ≈ 0 (декомпрессия на скорости RAM) |
| **PCM audio (FLAC/WAV)** | **WavPack -x** | binary | 87.2% ratio + 134 MB/s декод (B21). APE плотнее (86.6%) но декод 19 MB/s |
| FLAC lossless (density) | **flacr: APE -c4000 + recipe** | binary | Bit-exact реконструкция (b3sum 5/5, B23); guard `ape+recipe<flac`; экономия ~3–5% на реальной CD-музыке |
| PCM audio (архив/холодное) | APE -c4000 | binary | Максимальная плотность, медленный декод — только холодные данные |
| **MP3 (MPEG-1 Layer III)** | **pmp: packMP3** | binary | Bit-exact рекомпрессия −9…−12% (B28). Вдвое больше, чем даёт ZSTD-19 на том же файле |
| MP3 (MPEG-2 / 2.5 Layer III) | Store raw → ZSTD-19 | binary | packMP3 отказывается; падаем в generic-путь |
| Opus / Vorbis audio | Store raw | binary | Уже lossy-сжат |
| JPEG cover art | JXL lossless | binary | Подтверждено: 82.12% avg, bit-perfect 8/8 (B17) |
| PNG cover art | JXL + delta | binary | JXL умеет PNG (требует бенчмарка) |
| **ТЕГИ/метаданные (ID3v2, APEv2, XMP)** | **ZSTD-19 + dict** | text | Горячий путь: декод 100+ MB/s. PPMd запрещён (8.5 MB/s = 60мс на батч!) |
| **Мелкий текст (< 64KB, индивид.)** | **ZSTD -19** | text | PPMd непригоден на малых блоках |
| **Батч текста (1–4 MB, холодное)** | **PPMd o=16** | text | Лучший ratio (+12–14% над ZSTD -19 на любом блоке, B27) — только редко читаемое: декод ~12 MB/s = 84 мс на 1M-блок |
| **Мелкий текст с ZSTD-словарём** | **ZSTD -19 + dict** | text | Опция: обученный словарь даёт контекст малым блокам без батчинга |
| Executables C/C++ (EXE, DLL, ELF) | BCJ2 + ZSTD -19 | binary | Быстрая декомпрессия, хороший ratio |
| Executables Go | ZSTD -19 (БЕЗ BCJ2) | binary | BCJ2 ухудшает ratio Go-бинарников (B9) |
| Archives (low compression) | Recompress entries | varies | Декомпозиция, рекомпрессия |
| Archives (max compression) | Store raw | binary | Выигрыша нет |
| Encrypted / random data | Store raw | binary | Несжимаемо |
| Unknown binary | ZSTD -19 | binary | Безопасный дефолт |
| Бинарь (холодное, не mmap) | LZMA2 | binary | +7.8% над ZSTD -19 стабильно (B27), декод ~130 MB/s — на порядок дешевле PPMd |

## Размер сегмента по зонам (B27)

Сегменты AST сжимаются **независимо**, поэтому размер сегмента —
это и есть окно кодека. Единая константа `SEGMENT_SIZE` 64 KB на всю ФС
неоптимальна: текст сильно выигрывает от укрупнения, бинарь почти нет,
а платит за укрупнение mmap-нагрузка.

| Зона | Сегмент | Обоснование |
|---|---|---|
| RAW | 64 KB | Горячий путь записи, LZ4; латентность важнее плотности |
| Text | 1 MB | −15.2% байт против 64K (ZSTD -19: 5.575× → 6.576×) при латентности 0.71 мс |
| Binary | 256 KB | 64K → 1M даёт всего −7.5% байт, но ×16 латентности page fault; 256K — −4.3% при ×4 |

4 MB отклонён: на тексте всего +5.1% ratio поверх 1M за четырёхкратную
латентность, на бинаре 6.3 мс на page fault (уровень HDD-seek), плюс
4 MB резидентной памяти на каждый открытый файл в модуле ядра.

**ZSTD-22 и `--ultra` исключены из проекта.** Против -19 это +0.14%
ratio при вдвое более медленной компрессии и **худшей декомпрессии**
(979 против 1517 MB/s на 4M). Окно 128 MB у -22 не активируется, пока
блок независим и меньше ~32 MB.

Побочный эффект: `num_blocks` (`uint16`, 65535 сегментов) при 64K даёт
ровно 4 GB на файл, при 1M — 64 GB. Укрупнение сегмента само снимает
одну из двух границ 4 GB.

## Требование батчинга для текста

PPMd требует ≥ 64KB входных данных. Поэтому:

```
Sweep accumulator (text):
  [tag_A] [tag_B] [tag_C] ... → накопить до 64KB
  → PPMd -9 на весь батч
  → AST рецепты ссылаются на оффсеты внутри батча
```

Если батч не набрался (медленный приток данных) → ZSTD -19 для текущего накопленного куска.

## ZSTD Dictionary для мелких текстов

Альтернатива батчингу для критичных по задержке мелких блоков:

- Обучить словарь на выборке тегов (BLAKE3-стабильный, хранится в Metadata Zone)
- Каждый мелкий блок сжимается ZSTD -19 с этим словарём
- Словарь даёт LZ-матчеру "контекст", которого не хватает на малых входах
- Ожидаемый выигрыш: ~2x против ZSTD без словаря на 1-4KB блоках
- Требует бенчмарков на реальной библиотеке тегов

## Tag Block Delta System

При редактировании тега хранится только дельта:

```
Tag block v1: {artist: "Beyonce", album: "Lemonade"}
     ↓ edit
Delta log: append {artist: "Beyoncé"} at path "artist"
     ↓ read
Apply delta over base → {artist: "Beyoncé", album: "Lemonade"}
```

Дельта — десятки байт, append-only в Text Zone. Sweep периодически компактирует дельты в свежий базовый блок.

## Профили пользователя (конфигурируемая матрица)

Пользователь выбирает профиль — матрица алгоритмов не жёсткая:

```
profile = "balance"   # по умолчанию: WavPack/ZSTD/JXL — скорость+плотность
profile = "density"   # APE -c4000 / PPMd / Brotli — максимум плотности
profile = "speed"     # FLAC-raw / LZ4-HC — максимум скорости чтения
```

Пример конфигурации:
```ini
[audio]
*.flac = ape            # профиль density
*.mp3  = pmp            # packMP3, bit-exact (MPEG-1 Layer III)
[image]
*.jpg  = jxl
[text]
*.json = ppmd           # редко читается — плотность
*.md   = zstd
```

## Метрика: «× realtime» вместо MB/s

Для аудио критичен порог realtime (CD = 176.4 KB/s). Все кодки далеко выше:

| Кодек | Размер (от WAV) | Encode | Decode |
|-------|-----------------|--------|--------|
| FLAC -8 | 93.1% | 138× rt | 1260× rt |
| FLAC -5 | ~94% | 330× rt | ~1250× rt |
| WavPack -6 | 87.15% | ~100× rt | 760× rt |
| APE -c4000 | 86.64% | 127× rt | 108× rt |
| APE -c5000 | 86.63% | 63× rt | ~108× rt |

Даже APE -c5000 декодирует трек 3 мин за 1.7 сек — выше realtime, seek некритичен.
Seek: AST → только нужные сегменты → ARC-кэш (повторные seek — из RAM).

**Решение по APE:** -c4000 (не -c5000 — 0.01 пункта плотности за 2× encode). Доступен в профиле «density», НЕ по умолчанию (декод 108× rt vs 760× у WavPack).

## Кейс: PNG Repack Bruteforce (2025-08, проверено)

PNG = чанки (IHDR/PLTE/tEXt/...) + **IDAT** (единый zlib-поток, может
быть разрезан на несколько IDAT-чанков). Замена IDAT на JXL lossless +
рецепт даёт −26…−48% на фото-подобных PNG (замер: cjxl `-d 0 -e 9`:
3000×3000 фото 3.8MB → 1.99MB (−48%); 1000×1000 → −26/−28%).

### Почему не «угадать фильтры», а распаковать (секрет плана)

IDAT распаковывается (zlib inflate) → получаем **отфильтрованные данные**
(первый байт строки = фильтр 0-4). Но **фильтры НЕ восстанавливаются
из RGB**: выбор фильтра — решение энкодера, потерянное при декодировании.
Поэтому в рецепт пишем сами фильтры — **1 байт на строку** (3000 строк =
3KB, микро). Rebuild: JXL → RGB → refilter (фильтры из рецепта,
детерминированно: filt = orig − pred mod 256) → deflate-replica → IDAT.

### Брутфорс энкодеров (офлайн, секунды на файл — горячий путь не тронут)

IDAT пережимается всеми библиотеками-энкодерами и сравнивается с
оригиналом **BLAKE3/memcmp** (никаких «% совпадения» — deflate как домино:
одна неверная ссылка ломает весь хвост; совпало 99.9% = файл битый).

Набор энкодеров (статически слинкованные, как zlib 1.3.1 в gzip-кейсе):
- **zlib 1.2.11 / 1.2.13 / 1.3.1** — libpng-стандарт (проверено: реальный
  libpng-PNG OptimFROG SDK 1920×960 → MATCH `level=7 memLevel=9`);
  deflate-потоки 1.2.13 ⇄ 1.3.1 байт-в-байт идентичны (gzip-кейс).
- **zlib-ng 2.x** — ffmpeg/ImageMagick-сборки (размер совпал 855==855,
  байты отличаются — нужна точная версия или guard).
- **libdeflate** (png-оптимизаторы), **miniz** (наш собственный код).
- **zopfli/ECT/optipng-пересжатые** — НЕ реплицируются → guard.

### Результат (3 исхода)

1. **MATCH**: в AST-рецепт: `png_repack, encoder=zlib_1.3.1_7_9, filters[]` —
   оригинальный IDAT удаляется; чтение: JXL → RGB → refilter → deflate →
   IDAT + оригинальные non-IDAT чанки (хранятся как есть) → PNG 1:1.
2. **Pровал репликации** (zopfli/неизвестный энкодер): **guard — оригинал
   остаётся** (инвариант!), рядом пишется JXL-кэш для быстрого превью
   (sweep-выигрыш только от превью-скорости, не от размера).
3. **Невыгодно** (палитровые 2-4 бит, иконки): `JXL + рецепт >= PNG` →
   оригинал. (Пример: 2-бит палитровый 1920×960: IDAT 16963 → deflate
   −3% — JXL не даст больше.)

Ограничения первой версии: interlace=0 (Adam7 → guard), depth 8 RGB/RGBA/
palette — остальное → guard (безопасно, ничего не теряется).

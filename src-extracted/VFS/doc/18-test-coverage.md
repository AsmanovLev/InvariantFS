## 1. Сводка

Числа ниже — фактические: сколько `Assert` реально выполняется за прогон
(часть площадок вызывается в цикле, поэтому проверок больше, чем строк с
`Assert` в файле). Считаны прогоном, а не по оглавлению.

| Набор | Файл | Проверок | Окружение | Время |
|-------|------|----------|-----------|-------|
| Ядро/транскоды | `tests.ps1` | 131 | Windows CLI | ~10 мин |
| Dokan (Windows-FS) | `tests_dokan.ps1` | 26 | Windows + докан-демон | ~15 мин |
| FUSE (Linux/WSL2) | `tests_fuse.ps1` | **0** | `wsl -d void` + fusermount3 | ~5 мин |
| fsck/repair | `tests_fsck.ps1` | 13 | Windows CLI + WSL python | ~2 мин |
| **Итого** | | **170** | | |

Из 131 проверки `tests.ps1` две (T23) — это запуск `invf-arc-test.exe`, за
которым стоят ещё 4467 внутренних проверок инвариантов ARC; в общий счёт они не
входят, иначе одна подсистема перевесила бы всю таблицу.

`tests_fuse.ps1` не содержит ни одного `Assert`: он запускается, печатает и
всегда завершается успехом. Раньше в этой таблице ему приписывалось 7 проверок —
их там нет. Пока он не переписан, FUSE-бэкенд считается непокрытым.

**Главный инвариант, который защищают ВСЕ тесты:**
> **1:1 — записанное возвращается байт-в-байт.** Контейнеры хранят
> оригинал; транскод применяется только там, где bit-exact доказано;
> иначе — оригинал.

Запуск:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tests.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File tests_dokan.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File tests_fuse.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File tests_fsck.ps1
```

Сборка перед запуском: `cmd /c build_with_env.bat` (Windows),
`wsl bash build_linux.sh` (Linux CLI; `invf-fuse` собирается отдельно).

## 2. tests.ps1 — ядро и транскоды (131 проверка, 104 площадки Assert)

| Тест | Что покрывает | Ключевые проверки |
|------|---------------|-------------------|
| **T1** mkfs 4GB | Форматирование, суперблок, зоны | verify: CLEAN, uuid, метаданные |
| **T2** спарс-файл | Инвариант пустых областей | Запись с пробелами — байты на месте |
| **T3** покрытие зон | Разметка RAW/SHADOW/metadata | Сумма зон = том; нет пересечений |
| **T4** повреждение суперблока | CRC32C суперблока | Флип байта → `verify` FAIL |
| **T5** повреждение битмапа | Битмап vs аллокации | Флип бита → mismatch |
| **T6** UUID | Генерация | Два mkfs — разные uuid |
| **T7** минимальный размер | Граничные размеры | mkfs 64MB работает |
| **T8** пересоздание | Идемпотентность mkfs | mkfs поверх существующего |
| **T9** cp/cat bit-perfect | **Инвариант 1:1** | текст + исходник + exe: b3sum совпадает |
| **T9b** LZ4 в RAW | Сегментное сжатие | Файл занимает меньше блоков, чтение цело |
| **T10** отсутствующий файл | Ошибки доступа | cat/stat несуществующего → ошибка |
| **T11** ENOSPC RAW | Переполнение зоны | Запись при полном RAW → «volume full», том цел |
| **T12** Sweep LZ4→ZSTD-19 | Транскод + освобождение RAW | bit-perfect ПОСЛЕ sweep; free вырос; повторный sweep — идемпотентен |
| **T13** ZIP-контейнер | Контейнеры 1:1 + члены-окна | Архив возвращается байт-в-байт; извлечение членов on-demand |
| **T14** zip-in-zip | Вложенность (глубина ≤16) | 1:1 + извлечение на лету |
| **T15** FLAC→APE | Транскод FLAC (flacx) | bit-exact реконструкция FLAC из APE+рецепта |
| **T15b** обложки PICTURE | Вынос cover + дедуп | Дубли обложек не занимают места |
| **T16** TAR-контейнер | Члены `name!partN` + IVFT | bit-exact rebuild TAR |
| **T17** tar.gz | GZIP-репликация (IVGZ) | Члены + рецепт, bit-exact |
| **T18** PNG Repack | JXL-lossless + IVPN | bit-exact PNG, рефильтрация строк |
| **T19** запись > 64 КБ | `INVFS_MAX_REC_LEN` | Файлы после большой записи видны; ls/stat/fsck согласны |
| **T20** перезапись | Замена файла + братья | Новое содержимое читается, братья убраны, при ENOSPC старое выживает |
| **T21** отказ транскода | `vol_transcode_abort`, порядок записей | tar и FLAC: 0 сирот, 1 живой файл, оригинал bit-exact на каждой точке сбоя |
| **T22** ranged read + ARC | `vol_read_range` на свёрнутых файлах, `arc.c` в сборе | gz/png/flac/tar: окна по 64 КБ == целому файлу, кэш отвечает; при `INVFS_ARC_BYTES=0` те же байты и нулевые счётчики |
| **T23** ARC (юнит) | `arc.c` в одиночку: вытеснение, ghost-хиты, адаптация `p`, отказ по размеру | 4467 внутренних проверок; скан из 200 файлов стоит рабочему набору ≤1 записи, после адаптации — ноль |

Дополнительно: `verify --deep` (полная CRC-проверка сегментов) — в T12/T13+.

T21 гоняет пути отказа через `INVFS_FAIL_CHILD=N` — она роняет N-ю и все
последующие записи блобов, как ENOSPC. Снаружи такую точку не подобрать: sweep
освобождает оригинал по ходу, и «заполнить том до нужного байта» не даёт
контроля над тем, какой именно ребёнок не ляжет. Переменная не установлена в
обычных прогонах.

T22 закрывает разрыв между двумя путями чтения: монтирование ходит через
`vol_read_range` окнами по 64 КБ, CLI — через `vol_read_file` целиком, и на
свёрнутом файле эти два пути никто не сравнивал. Расходились они не в байтах, а
в самом факте: у транскода нет декодируемых сегментов, только блоб плюс
рецепт-сиблинг, так что FLACR/TARR/GZR/PNGR проваливались в raw-ветку, где
длина блоба никогда не равна длине реконструкции — `vol_read_range` возвращал
−1, и через монтирование свёрнутый файл не читался вообще, хотя `invf-cat`
отдавал его байт-в-байт. Отсюда парная проверка на каждый кодек: с кэшем байты
совпадают **и** `hits > 0`, с `INVFS_ARC_BYTES=0` байты те же, а счётчики
нулевые. Без второй половины тест прошёл бы и на кэше, который присутствует, но
никогда не спрашивается.

T23 существует потому, что T22 показывает только лёгкую половину кэша —
вставку и попадание. Один файл на процесс: вытеснение, ghost-хиты, адаптация
`p` и отказ по размеру там не срабатывают ни разу, а ошибка в них не ломает
байты, только скорость, которой assert не видит. Юнит-тест проверяет
инварианты (`|T1|+|T2| ≤ c`, `|T1|+|B1| ≤ c`, вся история ≤ `2c`) после каждой
операции смешанной нагрузки и отдельно — то свойство, ради которого это ARC, а
не LRU: односкановый проход по 200 файлам не должен вымывать рабочий набор.

**Покрываемые модули:** `volume.c` (формат, L2P, битмап, атомарные записи),
`flacx.c`, `tarx.c`, `pngx.c`, `gzrepro.c`, `zip.c`, `crc32c.c`, `lz4.c`,
`miniz.c`, `sweep.c`, `arc.c`.

## 3. tests_dokan.ps1 — Windows (Dokan) (26 проверок)

| Тест | Что покрывает |
|------|---------------|
| **T-D1** сборка | `invf-dokan.exe` существует |
| **T-D2** образ + монтирование | mkfs, докан-демон, точка Y: |
| **T-D3** чтение bit-perfect | gost.exe/doc через докан: b3sum = исходник |
| **T-D4** запись bit-perfect | 13MB через докан → чтение/CLI bit-exact |
| **T-D5** чтение не мусорит образ | Чтение не меняет L2P/битмап |
| **T-D6** персистентность (remount) | Файл жив после KillDokan/StartDokan |
| **T-D7** verify образа | Том валиден после записи |
| **T-D8** on-demand sweep | Фоновый транскод по простою (INVFS_SWEEP_INTERVAL) |
| **T-D9** каталоги | mkdir/вложенные файлы/чтение через докан |
| **T-D10** ENOSPC | Заполнение 0.15GB случайными 4MB → STATUS_DISK_FULL на 27-м файле, чтение b0 bit-exact |

**Важные соглашения (найденные при отладке, зафиксированы в тестах):**
- .NET `Copy-Item` пишет Zone-ADS (92 байта) при чтении через докан —
  тесты используют `[IO.File]::ReadAllBytes/WriteAllBytes`;
- Close-flush требует паузы ~2-3с (фоновый flush/rebuild);
- dokan всегда открывает файлы RW (иначе WriteFile не приходит);
- пути нормализуются `\`→`/`.

**Покрываемые модули:** `dokan_fs.c`, `volume.c` (каталоги: `vol_mkdir`/
`vol_list_dir`/`vol_ensure_path`; ENOSPC: резерв+флор, STATUS_DISK_FULL).

| Тест | Что покрывает |

## 7. Известные пробелы покрытия (не покрыто)

- **WinFsp-бэкенд** (`winfsp_fs.c`) — тест `tests_winfsp.ps1` устарел
  (бэкенд заменён на Dokan), не поддерживается.
- **Чтение после порчи ДАННЫХ сегмента** (битые байты в RAW/SHADOW) —
  проверяется только `verify --deep` вручную, в автотестах не симулируется.
- **Восстановление из полного обрыва питания** (kill -9 демона
  в середине flush) — ручной сценарий, не автоматизирован.
- **Quota/EDQUOT**, **throttling (EAGAIN)** — политика описана в
  `doc/12-enospc-strategy.md`, кодом не реализована (только READONLY).
- **Права/ACL** (`doc/11`) — не реализовано, тестов нет.
- **Параллельные записи одного файла** (несколько потоков на один inode) —
  не тестируется.

## 8. Как добавить тест

1. Номер по схеме: ядро `T<n>`, докан `T-D<n>`, FUSE `T-F<n>`,
   fsck `T-F<n>` (в `tests_fsck.ps1`), продолжать существующую нумерацию.
2. Каждый тест обязан завершаться `Assert ($cond) "имя"` и печатать
   понятное имя; набор выводит итог `PASS/FAIL`.
3. Для сценариев повреждения образа используйте `build/bitflip.py`,
   `build/corrupt_crc.py` (через `wsl python3`).
4. Не используйте PowerShell-редирект `>` для бинарного вывода
   (`invf-cat`) — искажает байты; используйте `cmd /c` или
   `[IO.File]::ReadAllBytes`.

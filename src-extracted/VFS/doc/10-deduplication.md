# Дедупликация

## Content-Addressed Storage через BLAKE3

Каждый семантический компонент (текстовый блок, аудио-фрейм, JXL-обложка) хэшируется **BLAKE3** при записи в Shadow Space. BLAKE3 выбран за:

- ~10x быстрее SHA-256 на больших данных (AVX-2 оптимизации)
- Древовидное хэширование — параллельный расчёт на многоядерных системах
- Keyed hashing — возможность разделять хэши по типам данных (аудио, текст, бинарник)

## Уровни дедупликации

### 1. Блочная дедупликация (Content Index)

```
Content Index (BLAKE3 hash → block_id):
────────────────────────────────────────
3b5a7c... → Block 42  (refcount: 15)
f1e2d3... → Block 17  (refcount: 3)
a8b2c1... → Block 88  (refcount: 1)
```

Если 100 FLAC-файлов содержат одну и ту же обложку (одинаковый BLAKE3), в Binary Zone хранится **один** JXL-блок, а AST-рецепты всех 100 файлов ссылаются на `block_id=42`.

### 2. Семантическая дедупликация (секции ELF/PE)

Для разработчиков — ключевая фича:

```
Бинарник v1: [.text: hash_A] [.rodata: hash_B] [.data: hash_C]
Бинарник v2: [.text: hash_D] [.rodata: hash_B] [.data: hash_C]
                                        ↑
                              .rodata и .data дедуплицированы!
```

Magic Sniffer разбирает ELF/PE на секции, каждая секция хэшируется отдельно. При обновлении компилятора меняется только `.text`, всё остальное делится между версиями.

### 3. Дедупликация для разработчиков (node_modules, контейнеры)

| Сценарий | Эффект |
|----------|--------|
| 10 микросервисов с одинаковыми зависимостями | Одна копия каждой уникальной библиотеки в TextZone |
| Docker-образы (Ubuntu:20.04, Ubuntu:22.04) | Общие .so файлы дедуплицируются |
| CI/CD артефакты (100 коммитов, каждый — сборка) | Меняются только изменённые .o файлы |
| Виртуальные окружения Python / venv | Одна копия numpy, pandas и т.д. |

## Учёт ссылок (Reference Counting) — через L2P Journal

Каждый блок в Shadow Space имеет счётчик ссылок. **Все изменения refcount — только через L2P Journal**, чтобы гарантировать crash-safety:

```
Journal entry: DELTA(inode, block_id, -1)
  → записывается в журнал ДО изменения in-memory refcount
  → на replay: применяется атомарно
  → на монтировании: восстанавливается точный refcount
```

### Операции

- **При создании файла с существующим BLAKE3**:
  1. Поиск в Content Index → найден block_id
  2. Journal: `DELTA(inode, block_id, +1)`
  3. In-memory refcount++
  4. AST рецепт ссылается на block_id

- **При удалении файла**:
  1. Journal: `DELTA(inode, block_id, -1)`
  2. In-memory refcount--
  3. Если refcount == 0: блок помечается свободным (Bitmap journal entry)

- **На монтировании (replay)**:
  1. Читаем все DELTA записи из журнала
  2. Перестраиваем Content Index refcounts в памяти
  3. Блоки с refcount == 0 освобождаются

### Почему не in-memory

Если питание моргнёт между декрементом refcount в памяти и записью на диск:
- **Потеря decrement** → блок навсегда останется зомби (утечка места)
- **Потеря increment** → блок удалится, пока на него ссылаются другие файлы (data loss)

Журнал гарантирует, что после replay refcounts точны.

## Мгновенные снапшоты (CAS-based)

Благодаря AST-деревьям + BLAKE3, снапшот тома — это **0 байт и мгновенно**:

```
1. Копируем root_ast_hash в Metadata Zone (snapshot table)
2. Инкремент refcount всех блоков, на которые ссылается root AST
3. Снапшот готов

Восстановление:
  → смонтировать снапшот как read-only том
  → root_ast_hash указывает на состояние на момент снимка

CoW: изменения после снапшота пишутся в новые блоки,
старые блоки живут (refcount > 0) → снапшот не изменяется.
```

Идеально для бэкапов и CI/CD (состояние до/после каждого коммита).

## Bloom Filter для Content Index

Поверх B-tree индекса BLAKE3-хэшей — in-memory фильтр Блума:

```
Проверка дубликата:
  1. BLAKE3(content) → хэш
  2. Bloom Filter → "дубликата точно нет"?
     └─ ДА → дисковый I/O не происходит вообще (мгновенно)
     └─ НЕТ/возможно → полноценный поиск в B-tree

Параметры:
  false positive rate: 1% 
  размер: ~10 бит на запись → 1M уникальных блоков = 1.25 MB RAM
```

**Радикально ускоряет дедупликацию** — большинство записей новых данных не попадают в B-tree lookup на диске.

## Overhead

| Индекс | Размер на 1M уникальных блоков |
|--------|-------------------------------|
| Content Index (BLAKE3 → block_id) | ~40 байт × 1M = 40 MB |
| Refcounts (block_id → counter) | ~8 байт × 20M блоков = 160 MB |

Оба индекса хранятся в Metadata Zone и кэшируются в RAM.
